# Быстрый вопрос и выгрузка пользователей

Релиз `quick-answers-20260909-r1`, база `5b1c208b665b448ecd9428eb00fe304b71ce475d`.

## Пользовательский сценарий

На странице мероприятия и в форме отправки доступны вкладки «Артефакты» и «Быстрый вопрос». Вопрос не настраивается: пользователь вводит текст до 10 000 символов. Ответ принимается один раз на мероприятие при заполненном профиле и открытом приёме материалов. ФИО фиксируется вместе с ответом. Повтор идентичного запроса безопасен; попытка изменить сохранённый текст отклоняется. Баллы и артефакт за ответ не создаются.

## Выгрузки

В админке мероприятия кнопка «Быстрый вопрос · ФИО и ответы XLSX» создаёт отдельную таблицу из двух колонок. Полная XLSX-выгрузка мероприятия также содержит лист быстрых ответов.

В разделе пользователей кнопка выгрузки ведёт к общему отчёту «Пользователи бота и конверсия». Он содержит листы «Пользователи», «Конверсия» и «Методика» без ограничения в 100 строк интерфейса. Подтверждённые привязки Leader ID берутся из OAuth-привязок, а не из введённого вручную номера. Токены и ключи не выгружаются.

До этого релиза отдельной истории запусков бота и входов в приложение не было: используются явно обозначенные исторические признаки. Даты не восстанавливаются предположительно. Конверсия — пересечение доступных признаков, не хронологическая воронка.

Чат определяется через `TELEGRAM_CATALYST_CHAT_ID` либо сохранённую конфигурацию бота в Redis. Для достоверной проверки известных Telegram ID бот должен быть администратором. Ошибка проверки означает «Неизвестно», а не отсутствие в чате. Общий счётчик Telegram включает ботов; участников, которых нет в базе приложения, перечислить через Bot API нельзя. Проверки последовательные с ограничением частоты. Файл хранится по стандартным правилам временных администраторских экспортов.

## Обновление

1. Сохранить исходники, текущий env, версии образов и PostgreSQL `pg_dump -Fc`.
2. Убедиться, что локальный код и GitHub указывают на один коммит.
3. Собрать приложения. Для ограниченного по памяти production-сервера допустим перенос готовых JS/Next standalone-сборок в существующие runtime-образы при неизменном `package-lock.json`. Linux native-зависимости в таком случае остаются из серверных Alpine-образов; переносить локальные `node_modules` нельзя.
4. Создать новые образы API, worker, bot, web и tools с одним тегом и OCI-меткой коммита. Для web переносить актуальную standalone-папку приложения, static и public, исключив старые файлы приложения в новом слое образа.
5. Выполнить штатный `migrate` с новой миграцией `0022_quick_answers_user_exports`. Не запускать seed/reset.
6. Обновить исходники `/opt/CPI-TG-BOT`, изменить только `IMAGE_TAG` в production env и пересоздать четыре приложения через Compose `up -d --no-deps --no-build`.
7. Проверить health, метки коммита, исходники и формирование реального пользовательского XLSX.

## Откат

Резервная копия: `/opt/CPI-TG-BOT/backups/quick-answers-20260909-r1`.

При откате приложений восстановить сохранённые образы по каждому сервису и предыдущие исходники/env. Миграция аддитивная: таблицу ответов и новые колонки не удалять, чтобы не потерять ответы после релиза. Не восстанавливать старый дамп поверх рабочей базы без отдельного решения: это затронет новые пользовательские данные.
